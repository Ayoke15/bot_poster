# Telegram → VK Autoposter · Go

Telegram-бот переносит текст, одиночные фотографии и их подписи из подключённого канала на стену сообщества VK. Настройка — в личном чате с ботом. Go 1.26+ и PostgreSQL 16; Docker-сборка и CI используют Go 1.27.3. Python больше не требуется.

## Запуск

Нужны собственный бот Telegram, публичный HTTPS-домен и ключ шифрования. Приложение при запуске регистрирует webhook и проверяет его раз в минуту. Используйте отдельного бота для разработки: регистрация заменяет его текущий webhook.

```sh
cp .env.example .env
# Заполните значения в .env, не добавляйте его в Git.
# TOKEN_ENCRYPTION_KEY: openssl rand -base64 32
# TELEGRAM_WEBHOOK_SECRET: openssl rand -hex 24
# Для DATABASE_URL задайте пароль с URL-кодированием специальных символов.
docker compose up -d --build
```

Приложение доступно локально на порту 8000. Настройте внешний HTTPS reverse proxy на этот порт и задайте его адрес в `APP_BASE_URL`. Встроенного выпуска TLS-сертификатов нет. Шаблон Nginx в `deploy/` рассчитан на размещение за TLS-прокси и сеть, в которой доступен DNS `app`; в Compose он автоматически не запускается.

Для запуска без Docker установите Go и PostgreSQL, экспортируйте переменные из `.env.example` через вашу систему секретов/окружения, замените хост `db` на адрес БД и выполните:

```sh
go mod download
go build -o bin/bot ./cmd/bot
./bin/bot
```

Go-приложение само не читает `.env`; файл читает Docker Compose. `LISTEN_ADDR` по умолчанию `:8000`, также поддерживается `PORT` (Railway). Для внешнего PostgreSQL используйте TLS согласно настройкам провайдера. В контейнере процесс работает без root. БД не публикуется наружу.

## Переменные

| Имя | Назначение |
| --- | --- |
| `DATABASE_URL` | PostgreSQL, права на создание/обновление таблиц |
| `TELEGRAM_BOT_TOKEN` | Токен бота из BotFather |
| `TELEGRAM_WEBHOOK_SECRET` | 16–256 символов `[A-Za-z0-9_-]`, секрет пути и заголовка webhook |
| `APP_BASE_URL` | Публичный базовый HTTPS URL без query/fragment |
| `TOKEN_ENCRYPTION_KEY` | Base64 от 32 случайных байт, ключ AES-256-GCM |
| `VK_API_VERSION` | По умолчанию `5.199` |
| `LISTEN_ADDR` / `PORT` | Адрес/порт HTTP-сервера; `LISTEN_ADDR` имеет приоритет |

Храните ключ шифрования отдельно от БД и делайте его защищённую резервную копию. Приложение проверяет расшифровку сохранённых токенов при старте и отказывается запускаться с неверным ключом. Автоматической ротации ключа нет. VK-токен пользователь передаёт в личный чат бота. Поддерживаются ключ выбранного сообщества с правом `wall` и пользовательский ключ VK API редактора/администратора группы с разрешением `wall`. Callback API и Long Poll API VK для публикации не нужны.

При ограниченном исходящем доступе нужны `api.telegram.org` и `api.vk.com`; для сборки — реестры Go-модулей и контейнеров. Не отключайте TLS или проверку сумм модулей.

## Подключение

1. `/start` или `/help` — инструкция; кнопки старого меню сохранены.
2. Добавьте бота администратором канала.
3. `/connect_channel -1001234567890` — явная привязка канала. Бот проверяет тип чата, ваши права и свои права через Telegram API. Другой пользователь не может перезаписать существующую привязку. Права повторно проверяются перед каждой доставкой.
4. «🔗 Подключить VK»: сначала ссылка вида `vk.com/club123`, затем ключ сообщества с правом `wall` (или пользовательский ключ редактора/администратора группы). Альтернатива: `/set_vk 123 <токен>`. Для пользовательского ключа проверяются разрешение `wall` через `account.getAppPermissions`, административная роль, `can_post=1` и включённая стена. Если этот вызов возвращает код 27, ключ проверяется как ключ сообщества через `groups.getTokenPermissions`: обязательны право `wall` и совпадение собственного ID сообщества, полученного без `group_ids`, с выбранной группой. Признаки пользовательской роли и `can_post` не используются для ключа сообщества. Право `photos` проверяется фактическими API-вызовами при загрузке фотографии; для текстового автопостинга оно не обязательно. Заблокированная группа и явно отключённая стена отклоняются. Если доступ запрещён или VK не вернул подтверждение, новый токен не сохраняется, а бот объясняет причину. При временной ошибке VK бот предлагает повторить подключение позже. Прежние настройки при отказе сохраняются. Пробный пост не создаётся; проверка не гарантирует отсутствие будущих ограничений, сбоев или отзыва прав при реальной отправке. Сообщение с токеном бот пытается удалить; Telegram может отказать, тогда удалите его самостоятельно. В ответах токен не показывается.
5. `/enable` — начать перенос новых постов. `/status` — настройки, количество ожидающих/неуспешных заданий и последние безопасные причины ошибок.

**Один Telegram-пользователь — одно текущее сообщество VK.** Связь и зашифрованный токен хранятся в одной строке `poster_users`, уникальной по `user_id` (PRIMARY KEY). Сохранение выполняется через `INSERT … ON CONFLICT(user_id) DO UPDATE`: повторное подключение заменяет группу и токен, а не добавляет вторую связь. Другие пользователи сохраняют собственные настройки. Бот заранее предупреждает о замене в инструкции и пошаговом подключении; после успешной замены сообщает старый и новый ID группы и число отменённых заданий.

`/disable` отменяет ожидающие задания. `/disconnect_channel <id>` отключает свой канал; `/clear_vk` удаляет зашифрованный ключ и выключает автопостинг. Замена VK-реквизитов отменяет старые задания, чтобы они не попали в другое сообщество. Уже выполняющийся внешний запрос может завершиться после отключения.

## Доставка и редактирование

- Webhook проверяет и секрет пути, и `X-Telegram-Bot-Api-Secret-Token`. Обновление считается принятым только после транзакции PostgreSQL. Ошибка БД даёт HTTP 503, чтобы Telegram повторил доставку.
- `poster_events` хранит уникальный `update_id` без исходного JSON и токенов. `(chat_id, message_id)` уникально в `poster_posts`; там же сохраняется `vk_post_id` и версия текста. Неизвестные каналы игнорируются, владельцы автоматически не назначаются.
- Новые посты доставляются фоновым воркером. Редактирование обновляет **тот же** пост через `wall.edit`. Устаревшее редактирование не затирает новое. Изменения неизвестных/старых постов игнорируются; изменения окончательно неуспешных и отменённых заданий тоже. Если пост стал полностью пустым (нет текста и фото), пост VK остаётся как есть, владелец получает ошибку. Фото с пустой подписью поддерживается. Удаления Telegram-постов не синхронизируются; видео и документы не переносятся.
- Задания переживают рестарт. Между репликами один воркер выбирается advisory-lock PostgreSQL. Лизинг задания сохраняется до HTTP-запроса; после сбоя оно становится доступно через 60 секунд.
- Сетевые сбои, HTTP 429/5xx и временные ошибки VK повторяются с задержками, максимум 6 попыток. Для создания поста используется один и тот же `guid`; после 45 минут с первой попытки повторное создание прекращается. Это ограничивает риск дублей при потерянном ответе в пределах окна дедупликации VK, но не является распределённой гарантией exactly-once. После исчерпания попыток проверьте стену VK вручную, прежде чем публиковать заново.
- Постоянные ошибки и исчерпание повторов остаются в БД, а уведомление владельцу сохраняется в отдельной очереди. Неотправленные уведомления повторяются с ограниченной максимальной задержкой. При блокировке бота уведомление может не дойти; причина публикации доступна через `/status`. Уведомление может повториться после сбоя между Telegram API и фиксацией БД.
- Логи и ошибки не содержат токенов, URL Telegram с токенами или исходных ответов API. Тексты постов и ID хранятся в БД; ограничьте доступ и настройте срок хранения/резервное копирование по своим требованиям. Автоматическая очистка истории не включена, чтобы не потерять дедупликацию.

## Фотография и подпись

Фото из Telegram (`message.photo`) переносится вместе с подписью в одну запись VK. Без подписи фото также публикуется. Выбирается самый большой доступный размер фотографии. Файл скачивается через Telegram `getFile`, загружается через `photos.getWallUploadServer` → multipart upload → `photos.saveWallPhoto` и прикрепляется к `wall.post`. Если VK отклоняет wall upload с кодом 27 для ключа сообщества, используется поддерживаемая пара `photos.getMessagesUploadServer` → `photos.saveMessagesPhoto`. Полученное вложение прикрепляется к стене; отправки сообщений VK нет.

Поддерживаются JPEG/PNG до 20 MiB (ограничение скачивания Telegram Bot API). Фото, отправленное как документ, видео и анимация пока не поддерживаются. Альбомы не объединяются: каждое фото Telegram приходит отдельным сообщением и создаёт отдельный пост.

При редактировании подписи обновляется существующий VK-пост. Загруженное вложение и его Telegram `file_id` сохраняются в PostgreSQL: повторы публикации и изменения одной подписи переиспользуют фото; замена самой фотографии загружает новое. Миграция добавляет три колонки в `poster_posts` и сохраняет старые текстовые задания. Сбой между сохранением фото в VK и фиксацией кеша в БД может оставить неиспользованную копию фото; повторный `wall.post` по-прежнему использует прежний `guid`.

Для загрузки ключу VK может потребоваться дополнительное разрешение `photos` вместе с `wall`. Ошибки загрузки сохраняются в задании и обрабатываются общей логикой повторов/уведомлений. При ошибке фото подпись отдельно не публикуется. URL скачивания Telegram с токеном, подписанные upload URL и ответы с хешами не выводятся в ошибки и логи.

## Проверки состояния

- `/live`: процесс отвечает, без проверки зависимостей.
- `/health`: HTTP 200 только если БД доступна, воркер активен и webhook проверен за последние 3 минуты. Иначе HTTP 503 и отдельные флаги `database`, `worker`, `webhook`. Недавние ошибки доставки Telegram также делают webhook неготовым.
- Невозможность регистрации webhook отражается безопасным предупреждением в логах; сервер остаётся доступен для диагностики и повторяет регистрацию.

## Переход с Python

Сохранённый тег старой версии: `snapshot-2026-11-02`.

1. Остановите Python-сервис и его реплики. Сделайте **проверенную резервную копию БД** и сохраните старую конфигурацию. Старый и новый сервисы нельзя запускать на одном боте одновременно.
2. Задайте постоянный `TOKEN_ENCRYPTION_KEY` и остальные переменные. Запустите Go-сервис с прежним `DATABASE_URL`.
3. Транзакционная миграция переносит пользователей, группы и токены из `user_settings`/`vk_accounts` в таблицы `poster_*`. Токены шифруются, старые поля `access_token` очищаются, старый автопостинг выключается. Повторный запуск миграции безопасен. Старые резервные копии всё ещё могут содержать открытые токены — защитите их.
4. **Каждый владелец заново выполняет `/connect_channel`, затем `/enable`.** Старые автоматические связи каналов не считаются доказательством владения и не импортируются.
5. Проверьте `/health`, `/status`, пробный пост и его редактирование в тестовом сообществе.

Откат Python требует восстановления **резервной копии до миграции**: в старых таблицах токены уже очищены, новый журнал доставок Python не понимает. Не откатывайте код поверх мигрированной рабочей БД и не перепубликуйте старые события вслепую. Приложение не делает бэкап автоматически.

## Тесты

```sh
go test -race ./...  # модульные тесты; интеграционные пропускаются без TEST_DATABASE_URL
go vet ./...
# Укажите отдельную тестовую БД с правами CREATE SCHEMA; каждый тест создаёт свою схему.
TEST_DATABASE_URL=postgresql://postgres:password@localhost:5432/poster_test make integration
```

Интеграционные тесты используют настоящий PostgreSQL и локальные HTTP-заглушки Telegram/VK: чужие каналы, повторные доставки, редактирование, временные/постоянные ошибки, потерянный ответ, шифрование/миграция, неверный ключ, отзыв прав и readiness. Реальные сообщения и публикации при тестировании не отправляются. CI поднимает PostgreSQL и выполняет эти проверки.

## Живой тест создания поста в PR

Обычная задача `test` в `.github/workflows/go.yml` запускается на каждом PR и push: модульные и интеграционные проверки с настоящим PostgreSQL и HTTP-заглушками API. Задача `Live Telegram to VK` включается repository variable `RUN_LIVE_INTEGRATION=true` и запускается после обычных проверок в PR из этого репозитория. Для форков и Dependabot она отключена. Запускайте её только для доверенного кода: он получает тестовые ключи.

Нужны отдельный Telegram-канал, один тестовый бот и тестовая группа VK. Владелец и бот должны быть администраторами канала, боту нужны права публикации. Используйте отдельного бота без webhook, чтобы пост не запустил одновременно развёрнутое приложение. Тест не читает очередь Telegram, не регистрирует webhook и не требует Callback API/Long Poll API VK.

GitHub → Settings → Secrets and variables → Actions:

| Тип | Имя | Значение |
| --- | --- | --- |
| Secret | `TG_TEST_BOT_TOKEN` | Токен единственного тестового Telegram-бота |
| Secret | `TG_TEST_OWNER_ID` | Telegram ID человека — администратора канала |
| Secret | `VK_TEST_COMMUNITY_TOKEN` | Ключ тестового сообщества с правом `wall` |
| Secret, необязательно | `VK_TEST_USER_TOKEN` | Альтернативный пользовательский ключ с правом `wall`; если задан, имеет приоритет |
| Variable | `TG_TEST_CHANNEL_ID` | ID Telegram-канала вида `-100…` |
| Variable | `VK_TEST_GROUP_ID` | Положительный ID тестового сообщества VK |
| Variable | `RUN_LIVE_INTEGRATION` | `true` для включения живого теста |

`VK_TEST_READ_TOKEN` и второй Telegram-бот больше не нужны. Токены не отправляйте в чат, PR или Git. Постоянный ключ шифрования и публичный HTTPS-адрес не нужны: ключ генерируется на запуск, PostgreSQL CI использует отдельную схему.

В CI выполняются два живых теста: текстовый (`sendMessage`) и фотография с подписью (`sendPhoto`, тестовый PNG генерируется в коде). Сценарий: настоящая публикация в Telegram → объект сообщения из ответа оборачивается в искусственный `channel_post` → дважды проходит локальный HTTP-обработчик для проверки дедупликации → настоящий воркер вызывает `wall.post`. Успех означает, что VK вернул положительный ID публикации и приложение сохранило результат в БД. Получение входящих событий Telegram, независимое чтение поста VK и его содержание не проверяются.

**Посты Telegram и VK не удаляются.** Они остаются для ручной проверки; в логе указан ID сообщения, ID VK-поста и ссылка на него. Каждый запуск создаёт новый пост с префиксом `autoposter-ci-`. Автоматически удаляется только временная схема тестовой БД. Тест не вызывает `wall.get`, `wall.getById`, `wall.delete` или `deleteMessage`.

Ключ сообщества проверен реальным вызовом `wall.post` в CI: публикация состоялась, но `wall.delete` тем же ключом получил код 27. Поэтому для сценария создания ключ подходит; поддержка чтения/удаления этим ключом не предполагается. Тестовая диагностическая запись https://vk.ru/wall-242994137_1 оставлена для ручной проверки.

Откройте или обновите PR из `feat/go-reliable-delivery` в `main`. Ждите зелёные задачи `test` и `Live Telegram to VK`; `SKIP` не подтверждает живую публикацию. Workflow также поддерживает ручной запуск после появления файла в основной ветке.

Локальный запуск с теми же настройками и отдельным `TEST_DATABASE_URL`:

```sh
RUN_LIVE_INTEGRATION=true go test -race -tags=live -run '^TestLiveTelegram(ToVK|PhotoToVK)$' -count=1 -timeout=7m -v ./internal/poster
```
